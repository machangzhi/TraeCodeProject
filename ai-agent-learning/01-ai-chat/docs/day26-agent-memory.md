# Day 26：Agent Memory —— conversation history 与「Memory ≠ 无限保存」

> 日期：2026-10-04
> 模型：deepseek-chat（temperature=0；Part A 为探针 Mock，零 API 成本）

## 设计要点

- Memory 本质是**消息管理策略**：LLM 无状态，"记得"的唯一实现是把历史消息放进本次请求。
- `ConversationMemory` 以"轮"为原子单位归档/裁剪，三种策略：`full` / `window K` / `tokenBudget`。
- 裁剪以轮为原子 ⇒ assistant(tool_calls) 与 tool 回传永不拆散，输出必过 R2' 协议闸（`checkMessageProtocol`）。
- Part B 对比唯一变量 = Memory 策略：full vs window K=1（同样的三轮对话，第 3 轮提问窗口策略才会真正裁掉记忆轮）。

## 学习笔记

1. **"记得"的唯一实现就是把消息放进本次请求。** 探针 Mock（T5/T6）给出了确定性证明：同一个探针 LLM、同一个问题，唯一差异是 Memory 策略——full 时它在 messages 里 grep 到 Alpha-7 答"记得"，window K=1 时 grep 不到答"不知道"。模型没有任何模型外的记忆：**Memory = messages 管理策略，裁掉即失忆**。
2. **失忆后模型眼中的世界被改写了，而且它不觉得自己失忆。** B2 第 3 轮的真实答复："你从未在对话中告诉过我你的项目代号""刚才我们只做了 8×3 的计算，我并没有查询过北京的天气"——从模型的视角这些话完全属实，因为它收到的上下文里确实只有第 2 轮。这不是模型说谎，是**上下文裁剪改写了它眼中的历史**。工程含义：被裁掉的信息不是"暂时想不起来"，而是永远消失；重要信息要么留在上下文里，要么显式外置（Day 27 之后的文件/数据库记忆）。
3. **窗口 K 的语义是"保留最近 K 轮"，失忆发生在 提问轮 − 记忆轮 > K 时。** 初版设计在此踩坑：两轮对话 + K=1，第 2 轮提问时第 1 轮恰好是"最近一轮"而被保留，失忆演示不会发生——把提问放到第 3 轮（T6/B2）才真正裁掉记忆轮。选窗口大小时要按"业务上允许隔多少轮还能接上话"来定，而不是拍脑袋。
4. **裁剪必须以"轮"为原子单位。** T3 验证了 K=2/K=1 两种裁剪下 R2' 协议零违规：一轮内的 assistant(tool_calls) 和 tool 回传永远同进同退。如果按消息条数裁（比如"只留最近 10 条"），边界随时可能落在 tool_calls 和 tool 回传之间，请求直接被 API 拒绝——这是 Memory 裁剪最经典的协议坑，轮原子性从结构上杜绝了它。
5. **消息数是成本的粗代理，不是精确账本。** B1 的 promptTokens 走势 1027→1372→739：第 3 轮消息最多（10 条）tokens 反而最低——因为 promptTokens 是该轮全部 LLM 调用的总和（第 1/2 轮是"带工具定义的决策调用 + 收尾调用"两次，第 3 轮模型直接读历史作答只调了一次）。看成本要看"调用次数 × 单次请求大小"，还要意识到**每轮都重复发送的工具定义本身就是固定开销**。
6. **窗口策略的真实节省可以量化。** 同一第 3 轮提问：B2 携带 6 条消息 prompt 531 tokens，B1 携带 10 条 prompt 739 tokens——少 4 条消息省约 28% 的该次请求开销，代价是代号和天气全部失忆（B2 判分如实证明）。"省多少 vs 忘多少"不再是一句口号，而是本实验里的一对具体数字。
7. **工具能力是请求级的，记忆是消息级的。** B2 第 3 轮失忆后模型仍主动提议"我可以现在帮你查一下北京的天气"——工具定义每次请求都随请求发送，不受记忆裁剪影响。所以失忆的 Agent 不会瘫痪，它退化为"功能正常但没有历史的助手"：能算能查，但不知道你们聊过什么。

## 概念卡片

- **Conversation History（对话记忆）**：跨轮维护的历史消息集合；LLM 无状态，"记得"的唯一实现是把（按策略裁剪后的）历史放进本次请求的 messages。
- **滑动窗口（window K）**：只保留最近 K 轮历史；成本有界（消息数恒定），代价是 K 之外的轮次永久失忆。
- **Token 预算（tokenBudget）**：window 的推广版——按估算 token 从最新轮往旧装，装不下即停（T4：50 预算只装下最近 2 轮）。
- **轮原子性**：裁剪以"轮"为最小单位，assistant(tool_calls) 与其 tool 回传同进同退，从结构上保证 R2' 协议永不破坏。
- **记忆边界**：模型只"知道"上下文窗口里存在的信息；被裁剪的历史不是想不起来，而是在模型的世界里从未发生过。

## 面试题

**Q1：LLM 是无状态的，"多轮对话记忆"到底是怎么实现的？**

A：把历史消息放进每次请求的 messages 数组。本实验用探针 Mock 做了确定性证明（T5/T6）：同一个探针 LLM 问同一个问题，full 策略时它在收到的 messages 里能找到标记词 Alpha-7 所以答"记得"，window K=1 裁掉该轮后就答"不知道"——模型侧没有任何存储，记忆 100% 来自请求携带的内容。B1 的真实运行同样证明：第 3 轮请求带 10 条消息（含第 1 轮的工具调用记录），模型同时答出代号 Alpha-7 和北京 22°C，一次调用都没有重发。所以 Memory 工程的本质不是"让模型记住"，而是"决定每次请求带哪些历史"。

**Q2：Memory 裁剪为什么必须以"轮"为原子单位？按消息条数裁会出什么问题？**

A：一轮 Agent 执行会产生 assistant(tool_calls) → tool 回传（可能多条）→ 最终 assistant 答复的消息组，协议要求每个 tool_call 的 id 必须有紧跟的同 id tool 消息（Day 24 的 R2 不变量）。如果按"保留最近 N 条消息"裁，边界随时可能落在 tool_calls 和它的回传之间，产生悬空 tool_calls，请求会被 API 直接拒绝。本实验的 ConversationMemory 以轮为原子单位归档，T3 验证了 K=2 和 K=1 两种裁剪结果都通过 checkMessageProtocol 零违规——轮原子性让"裁剪永不产生协议违规"成为结构保证而不是运气。

**Q3：全量保留、滑动窗口、摘要压缩三种记忆策略各有什么取舍？实际系统怎么选？**

A：本实验实证了前两种：full（B1）记忆完整——第 3 轮同时答出代号与天气，但每轮请求消息数线性增长（2→6→10），长对话成本持续上涨且终将撞上下文窗口上限；window K=1（B2）成本有界——同轮请求 6 条消息省约 28% tokens，但窗口外的信息永久丢失，模型甚至会说"你从未告诉过我"（B2 第 3 轮答复）。摘要压缩介于两者之间：把旧轮压缩成一条摘要消息保留语义、丢掉细节，但摘要有信息损失且本身要花一次 LLM 调用。选择依据是业务时效性：客服场景最近几轮基本够用（window/tokenBudget），需长期记住的用户偏好应显式外置到 profile/数据库并在 system prompt 注入，而不是指望对话历史无限保留——这正是"Memory ≠ 无限保存全部聊天记录"的含义。
