## 学习笔记

### 1. Agent 与"带工具的脚本"的区别：循环终止权交给了模型

Day 15-20 的编排是脚本控制的 for 轮次，本质是"我们替用户规定好最多走几步"。今天的 Agent Loop 只有一个终止条件：**模型不再发起 tool_calls**。

```text
finished = false
while (!finished) {
  resp = LLM(messages)
  if (resp.tool_calls 为空) finished = true   // 模型自己宣布：信息够了
  else { 执行工具 → 结果回传 }                // 模型自己决定：还需要什么
}
```

这意味着"任务是否完成"的判断从程序员手里转移到了模型——它根据已拿到的信息自主决定继续还是收尾。今天 7 个场景全部以 stopReason=finished 正常结束：简单问题 1–2 轮就收尾（A5 一轮、A1 两轮），链式问题 3 轮（A2/A3），模型没有无谓多调。这正是 Agent 的核心特征：**自主决策下一步 + 自主判断何时结束**。

### 2. A4 vs A7：同样是"查不到"，拦截位置完全不同

这是今天最有价值的对比设计。两个场景最终答复都包含"查不到"，但错误发生在不同层：

| | A4 火星基地 | A7 重庆 |
|---|---|---|
| 模型行为 | 零调用，直接解释火星无气象站 | 正常发起 get_weather("重庆") |
| 工具行为 | 未被调用 | execute 失败，返回 `{error, stage:"execute"}` |
| 机制 | **调用前语义拦截** | **调用后错误穿透** |
| LLM 轮数 | 1 | 2 |

- A4 中模型凭语义知识判断"火星基地不是真实地名，调了也白调"——这是智能，但**安全不能依赖它**（它也可能判断错，把真地名当虚构的、或反过来）；
- A7 中重庆是真实城市、模型无法预知 Mock 库只覆盖 4 个城市，所以诚实发起调用，由工具返回确定性的错误，再如实转述并给出替代渠道。

工程结论：**两道防线都要**。调用前拦截省一次往返（智能层），但工具内的确定性校验才是权威（执行层）。这也修正了我最初的判分错误——我误以为 A4 一定走错误穿透路径，却忽略了模型在调用前就有一次自主判断。

### 3. AgentStep：让每一轮循环都成为可检查的数据

今天把每轮循环结构化为 AgentStep：`iteration`（第几轮）、`kind`（tool_calls/final）、`assistantContent`（模型这轮的文字）、`toolExecutions`（每个调用的名称/参数/结果/失败阶段）。

这个结构立刻产生三个用途：

1. **判分**：toolSequence() 直接从 steps 算出"get_weather → calculator"，可以检查链式顺序、首轮是否并行；
2. **调试**：A4 首跑误判时，看 steps 就立刻定位是"没调用"而非"调用失败"；
3. **为 Day 27 UI 铺路**：模型在 tool_calls 轮常常同时输出旁白（如"我先查一下深圳的气温"），assistantContent 把这些思考和工具结果按时间顺序排列，就是前端"思考链"的天然数据源。

### 4. 循环必须有安全出口

`while (!finished)` 有一个理论风险：模型若每轮都坚持调用工具，循环永不结束。今天放了 TEMP_SAFETY_LIMIT=8 兜底——撞上限后 finished=true、answer 标注被迫停止。这不是今天的重点（Day 24 正式实现 MAX_ITERATIONS=10 及配套错误处理），但先确认了一件事：**任何由模型驱动终止的循环，都必须同时有程序控制的硬上限**，终止权可以交出去，但保险丝必须留在自己手里。

### 5. 迭代轮数与成本分布

定稿 7 场景共 14 轮 LLM 调用、prompt 8781 / completion 1062 tokens。观察轮数分布：

- 1 轮：A4/A5（无需工具或门前拦截）；
- 2 轮：A1/A6/A7（单工具或并行一轮）；
- 3 轮：A2/A3（链式：先取数据再计算）。

链式场景每多一环，全量工具定义就要重发一遍——多步 Agent 的成本随步数增长，这再次指向后续优化：步数上限、工具子集裁剪、精简工具描述。

## 概念卡片

- **Agent Loop**：`while (!finished)` 的自主循环，模型决策下一步动作、并以"不再调用工具"宣布完成。
- **finished 条件**：模型当轮未发起任何 tool_calls——任务完成信号由模型产生，而非程序预设步数。
- **AgentStep**：循环中一轮的结构化记录（序号、类型、模型旁白、工具执行结果），用于判分、调试与思考链展示。
- **调用前语义拦截 / 调用后错误穿透**：前者模型凭知识零调用（A4），后者工具执行失败后错误回传（A7）；智能层与执行层两道防线。
- **安全上限**：程序持有的循环硬兜底，防止模型驱动的循环失控（Day 24 正式化）。

## 面试题

Q：Agent Loop 和之前的工具调用脚本有什么本质区别？
> A：终止权不同。之前是程序用 for 预设轮数；Agent Loop 是 while(!finished)，finished 只在模型不再发起 tool_calls 时成立——"信息够了没有、下一步做什么"由模型自主判断。今天 7 个场景全部自主正常结束，简单问题 1-2 轮收尾、链式问题 3 轮，没有无谓调用。

Q：模型不调用工具直接回答，一定是偷懒吗？
> A：不是，要区分语义。A4"火星基地天气"模型零调用直接解释火星无气象站——调用前语义拦截，答案正确且省一次往返；但安全不能依赖这层判断，所以工具内必须有确定性校验。我们用 A7（重庆：真实城市但 Mock 未覆盖）对照验证了错误穿透路径：模型诚实调用、工具返回 execute 错误、模型转述并给出替代方案。两种机制缺一不可。

Q：怎么知道一个 Agent 任务里每一步发生了什么？
> A：每轮循环记录为 AgentStep：第几轮、是工具调用还是最终答复、模型的旁白文字、每个工具的参数与执行结果（含失败阶段）。从 steps 可以还原工具序列（如 get_weather → calculator）、检查首轮并行、定位失败位置；它也是 Day 27 前端思考链的数据源。

Q：模型控制循环结束，会不会有失控风险？怎么防？
> A：会有理论风险——模型若坚持每轮调工具，while 永不结束。所以必须保留程序侧的硬上限（今天临时设 8，Day 24 正式实现 MAX_ITERATIONS=10）。终止权可以交给模型，保险丝必须在程序手里。
