## 关键决策

1. **切分策略 = 文档结构，而不是字符数**。固定长度 500 字符会把「组件定义」和「响应式原理」混进同一个 chunk（Day 37 实测 vue3.md 只能切 2 段且语义混合），按标题切则天然落在语义边界上，还顺带产出 `heading` 元数据供来源展示。
2. **Metadata 分两级**：`category` 做互斥粗分类（vue / react / other），`tags` 做多值细标签。实测在英文 embedding 模型区分度不足时，`category=vue` 过滤直接把不相关的 react 文档挡在候选集之外，是最便宜的效果提升手段。
3. **上传走 `FileReader` + JSON 提交**，不引 multipart 依赖。代价是只覆盖文本类文档（`.md/.txt`），二进制还要再想办法；顺带踩到 `express.json` 默认 100kb 上限，已调到 2mb。
4. **上传后全量重建索引**：清库重灌，简单且幂等；重复文本命中 embedding 缓存，实际只付新 chunk 的算力（本地模型，¥0）。文档上量后必须换按文件增量。
5. **知识库列表以向量库为真相源**，不是目录。好处是「列出来的一定搜得到」；代价是目录里没入库的文件不显示（实测 `data/docs` 有 5 个文件、列表只有 3 个 `.md`），所以页面上配了「重建索引」按钮让用户手动对齐。
6. **Agent 与 RAG 开关互斥**：Agent 模式下模型自己决定调不调工具，RAG 模式下只查知识库——语义不同，不允许同时开。

## 遇到的问题与解决

| 问题 | 原因 | 解决 |
|---|---|---|
| 上传大文件 413 | `express.json` 默认 100kb | 显式设为 2mb |
| 目录里文件多、列表里文件少 | 列表源是向量库，入库只吃 `.md` | 记录为 V1 已知缺口，多格式入库统一后再对齐 |
| 检索排序不理想 | 英文模型对中文长查询区分弱 | 用 `category` 过滤兜底；根本解法是换中文模型 + Rerank（第 7 周） |
| 文档 H1 标题丢失 | H1 与 H2 之间无正文，flush 时按空段跳过 | 判定为正确行为：文档大标题不该占检索位 |

## 复盘题

### Q1：为什么说「结构化切分」比「固定长度切分」更适合知识库？
A：因为检索的基本单位应当是一个**语义完整的小节**，而不是一段等长文本。Day 37 的实测对照：同一份 vue3.md，固定长度只能切 2 个 chunk 且一个 chunk 里混了多个主题；按 H2 切出 3 个 chunk（组件定义 / 响应式原理 / 生命周期），每个都能独立回答问题。额外收益是切分时自然拿到了 `heading`，来源展示可以直接告诉用户"这句话出自哪一节"；而固定长度切分想拿到这个信息只能再反查原文。

### Q2：Metadata 过滤和向量检索解决的是同一个问题吗？
A：不是，两者互补。向量检索解决「语义相近」，但它会犯错——`all-MiniLM-L6-v2` 问「响应式原理」时 Top1 是 react 渲染机制（Day 38 实测）。Metadata 过滤解决「范围约束」，它是精确匹配、不依赖模型质量。所以正确顺序是**先过滤再排序**：既缩小候选集降低计算量，又保证返回结果一定落在用户指定的范围内。真正难的是过滤条件从哪来——用户显式指定最可靠，LLM 自动提取次之（可能提错），所以界面上给了分类下拉框让用户可控。

### Q3：V1 到这里就算"完成"了吗？还差什么？
A：按计划口径，V1 只要求「上传 / 列表 / 问答 / 来源」四项跑通，这四条已在浏览器端到端验证（Day 39，7/7）+ 验收脚本（Day 42，17/17）。但作为企业知识库还有三个明显缺口：(1) **没有评测集**——现在只能靠几个样例手测，回答正确率没有数字，第 7 周要建 30–50 条黄金问答集；(2) **没有质量防线**——相似度阈值、Rerank、Query Rewrite 全都没上，召回质量完全押在 embedding 模型上；(3) **注入风险**——文档内容直接拼进 prompt，没有防注入处理。这也正是第 7 周的三个主题。
