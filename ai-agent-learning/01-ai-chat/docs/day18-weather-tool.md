```text
这是个很好的问题！简单说，彩虹是阳光被空气中的水滴"折射—反射—再折射"后形成的。

**形成过程大致是这样：**

1. **需要阳光和水滴同时存在**：雨后空气里还悬浮着大量小水滴，同时太阳从云缝里露出来，条件就具备了。
2. **阳光进入水滴时发生折射**：白光进入水滴会偏折，并且不同颜色的光偏折角度不同（紫光偏得多、红光偏得少），于是白光被"拆开"成七色。
3. **在水滴内壁反射一次**，再从水滴另一侧折射出来。
4. **大量水滴共同作用**：每颗水滴都把光偏折到大约 42° 的方向，无数水滴叠加，就形成我们看到的弧形彩带。

**为什么夏天特别常见？**

- 夏天多对流雨（雷阵雨），来得快去得也快，雨后很快放晴，容易满足"一边下雨一边出太阳"的条件。
- 太阳高度角合适时（早晨或傍晚），彩虹更容易出现在地平线附近被我们看到。
- 观察彩虹时，太阳在你背后、水滴在你前方，所以彩虹总在太阳的对面方向。

**几个有趣的小知识：**

- 彩虹其实是个完整的圆，只是地面挡住了下半部分，在飞机或高山上有时能看到整圈。
- 有时能看到第二道彩虹（霓），颜色顺序是反的，那是光在水滴里多反射了一次的结果。
- 彩虹的位置和你的站位有关，所以它"跟着你走"，永远追不到尽头。

顺便一提，如果你想知道某个城市现在的天气适不适合碰运气看彩虹，我可以帮你查一下实时天气～
```

## 学习笔记

### 1. Mock 兜底的核心不是「假数据」，而是「可替换的 Provider 契约」

天气来源被抽象为 `WeatherProvider` 接口，当前只实现 `MockWeatherProvider`；将来接入真实 API（如免费免 Key 的 Open-Meteo）时新增 `LiveWeatherProvider`、按 env 切换即可——**编排循环、工具定义、判分器全都不用改**。这是开闭原则在 LLM 工具开发里的直接应用：外部服务不稳定（限流、宕机、收费变更），让"来源"成为唯一的可变点。

Mock 数据本身也经过设计：9 个城市共用**固定快照时间** `2026-10-04T10:00:00+08:00`，温度/湿度/降水全部写死。意义是可复现——今天重跑、下周重跑、别人拿到脚本重跑，gold 与输出完全一致，不会因真实天气变化而让历史实验失效。这与 Day 16 用 gold 表达式、Day 17 用同一瞬间 gold 是同一条评测纪律。

### 2. Mock 数据必须诚实：模型全程披露「非真实观测」

工具返回带 `dataSource: "mock"`，system prompt 明确要求转述时说明。8 个场景里模型无一漏标：

- S4 开头即写"数据来源：Mock 模拟数据，非真实实时观测"，结尾再补"实际出行请以官方气象台实时预报为准"；
- S5/S6 也都在标题或表头标注快照来源。

这件事的价值要对照 Day 16 的教训：那天模型自己伪造"计算器返回值"，把参数记忆包装成工具权威；今天我们反过来，**在协议层给数据打上真实来源标签**——Mock 就声称 Mock，不骗取用户信任。生产中同理：缓存数据标缓存时间、降级数据标降级状态，让下游能基于数据质量做决策。

### 3. 归一化在工具、翻译在模型：城市输入的两层处理

- 工具层做**确定性归一化**：`上海市`→去后缀→上海；`Tokyo`/`tokyo`/别名表→东京；拼音缩写 `bj/sh` 也收录。上线前用 7 条用例单测校准（含 null case），全 PASS。
- 模型层仍负责更模糊的消歧（如"江城"指武汉还是吉林市）——这类语义判断不适合写死在工具里。

边界划分的原则不变：**确定性规则进工具，开放性语义留模型，且安全校验不依赖模型**。S7 证明：即使模型把"火星基地"原样传入，工具也会确定性返回未知城市错误。

### 4. 工具给事实、模型做判断：S4 与 S6 是两种典型组合

- **S4 决策型**：模型没有止步于播报天气，而是基于 `precipitationMm=8`、`condition=中雨`、湿度 85% 推出"需要带伞，最好选长柄雨伞而非折叠小伞"，还结合体感 30°C 给出穿衣建议。事实全部来自工具，**推理价值由模型增量提供**。
- **S6 对比型**：模型同一轮并行发起两个 tool_calls，拿到同一快照的 22°C/28°C 后输出对比表格，正确指出"广州更热"，并比较了天气状况、湿度等字段。工具无法回答"哪边更热"——它只会逐城查询；跨工具结果的组织与比较是模型不可替代的部分。

这回答了"有了工具还要模型干什么"：工具扩展了模型的**感知与执行边界**，模型负责在多个确定事实上做推理、规划与表达。

### 5. 错误穿透 + 调用门：模式已完全成熟

- **S7**：工具错误信息带上了覆盖城市清单，模型转述后用户立刻知道"能查什么、下一步怎么问"——好的错误信息应可执行，不只是"失败了"。
- **S8**：问彩虹成因，模型零调用，讲齐了阳光、雨滴、折射/反射/色散三要素。

Day 16 修三轮、Day 17 修三轮，今天 8 场景首轮 8/8、判分器无误放无误杀。原因不是题目变简单，而是前两周沉淀的组件今天直接复用：编排循环（并行 tool_calls 配对、轮数上限）、错误穿透（{error} 不中断）、确定性 gold、归一化先单测。**模式成熟度本身就是学习成果**——这也为明天 Day 19 的 Tool Registry（统一注册 calculator/time/weather）做好了准备。

## 概念卡片

- **Provider 抽象**：把外部数据来源藏在统一接口后面，Mock/Live 可替换；外部服务不稳定时的标准解耦手段。
- **固定快照**：Mock 数据集使用写死的观测时间与数值，保证实验历史可复现。
- **数据来源标签**：返回中显式标注 dataSource（mock/cache/live），不把低可信度数据伪装成实时事实。
- **归一化（normalize）**：把多种等价输入（后缀、大小写、别名、拼音）映射为唯一规范键。
- **决策型/对比型工具组合**：模型基于工具事实做行动建议，或基于多个并行工具结果做比较——工具给事实，模型给判断。

## 面试题

Q：没有天气 API 就做不了天气功能吗？你们怎么处理的？
> A：把天气来源抽象成 WeatherProvider 接口，先实现 MockWeatherProvider：9 个城市的固定快照、归一化输入、未知城市返回结构化错误，编排层与工具定义完全不感知来源；将来接 Open-Meteo 等真实 API 只需新增实现并按 env 切换。关键是 Mock 数据带 dataSource 标签、模型全程向用户披露"非真实观测"，不骗取信任。今天 8 场景首轮即 8/8。

Q：模型怎么知道"出门要带伞"？它自己会判断天气吗？
> A：模型不判断天气，工具返回深圳 condition=中雨、precipitationMm=8、湿度 85% 这些事实；带伞结论是模型基于这些确定字段的推理，它还补充了"选长柄伞、穿透气衣物"。分工是工具感知事实、模型产出判断——Day 16/17 也一样，模型从不生成计算或观测结果。

Q：用户输入"上海市""Tokyo""bj"，你们怎么保证查到同一条数据？
> A：工具层做确定性归一化：去行政区划后缀、查别名表（英文、拼音、缩写），统一映射到规范键"上海/东京/北京"；归一化逻辑上线前用 7 条样本单测校准。更模糊的语义消歧留给模型，而即使模型传入无法归一化的城市（如火星基地），工具也会返回带覆盖清单的错误。

Q：Mock 数据为什么要固定时间？让它返回当前时间不行吗？
> A：固定快照是为了实验可复现——历史报告中的 gold 与输出不会因日期变化失效，这和单测不允许依赖当前时间是同一个道理。今天 S6 的冷热对比还依赖两个调用返回同一快照；若各自取当前时刻，跨调用间隔就可能引入争议。真实 API 接入时由 LiveProvider 自行管理观测时间，返回结构保持不变。
