## 分析与学习笔记

### 1. Rerank 精准治好了 Day 43/45 的病灶——这是今天最硬的一条证据

Day 43 定性：C1/C6 的 gold 被压在噪声下面（向量排第 5、距离 0.800/0.752 > 噪声 0.554/0.579）；Day 45 证明"水平切一刀的阈值治不了纵向排序错位"。今天 Part A 直接看到药效：**C1 的 gold 从第 5 提到第 1，C6 的 gold 从第 5 提到第 1**，且两者的**向量 Top1（react.md#渲染机制）都被纠正成了正确 chunk**。Part B 兑现：**无重排 K=3 的 5/7 变成重排 N20→3 的 7/7**。**结论：召回没问题（gold 一直在库里），问题只是排序；Rerank 正是那把对症的刀。**

### 2. "重排 N20→3" 是今天的 Pareto 最优：用更少的上下文拿到同样的正确率

对比四档：重排 N20→3 与无重排 K=5 **正确率都是 7/7**，但前者**平均噪声 1.57 vs 3.86（不到一半）**、**prompt 估算 ≈3144 vs ≈4041（少 22%）**。也就是说 Rerank 买到的不只是"更准"，还有"**更省**"——它把"靠加大 K 硬凑召回"换成了"靠精排把正确内容提到前面"。**这才是 Rerank 的真正卖点：既提正确率，也降上下文污染和成本。**

### 3. 重排后继续加大 K（N20→5）纯属浪费：第 4/5 位全是 0 分噪声

重排 N20→5 正确率仍是 7/7（没有任何提升），但噪声涨到 3.57、prompt 估算涨到 ≈4465。看它的 sources 就明白：重排后第 4、5 位是 `react.md#渲染机制(0.00)`、`react.md#状态管理(0.00)` 这种**零分**内容——精排已经把 gold 挤到前 2，后面全是"陪跑"。**结论：一旦上了 Rerank，K 就应该取小（本实验取 3 足够），大 K 是"重排前的习惯"的残留。**

### 4. Mock 打分器只能"分两段"，中段排序不可靠

重排后第 3 位经常是"次优噪声"：C1 第 3 位是 `vue3.md#组件定义(0.02)`（因为它的正文含"定义响应式数据"字面重合）、C2/C3 第 3 位是 `vue3.md#生命周期(0.09)`。分数分布也说明问题——0.19 → 0.03 之间没有平滑梯度。**词重合度打分器本质是"有字面重合 vs 没有"的二段判别**，它能把"明显不相干"压下去，但分不清"两个都有重合的谁更相关"。这正是它只能占位的原因：真机 cross-encoder 会同时读 query 和文档的**含义**，而不是数共同子串。**结论：今天验证的是"Rerank 这段链路 + 增益方向"，不是"真实 Rerank 模型的天花板"。**

### 5. 重排对"库里根本没有"的问题无能为力——兜底仍靠拒答/阈值

C7（天气）在词重合度下 **9 个 chunk 全部 0.00 分**，稳定排序下顺序原封不动（Top1 仍是 react.md#状态管理）。模型照样正确拒答，但这是**模型在兜底，不是 Rerank 在兜底**。**结论：Rerank 只做"相对排序"，不生产"绝对相关性"，所以"库外问题"必须由阈值短路（Day 45）或模型拒答来管，两者正交。**顺带一个有意思的细节：这也说明 Day 45 的阈值与 Day 46 的 Rerank 是**互补而非替代**——阈值管"整批都远"，Rerank 管"远近混杂但错的排前面"。

### 6. 一个必须写明的规模警告：`TopN=20` 在本库实际等于"全库 9 条"

计划要求的是 `Top 20 → Rerank → Top 5`，但本库只有 9 个 chunk，**`rerankTopN=20` 实际等价于不截断**。这意味着今天的实验**没有覆盖"粗排截断"这一面**——真实库里 N=20 是从上千条里筛出来的，重排要处理的是"召回面本身可能漏掉正确 chunk"的问题（那是 Recall@N 的锅，Rerank 救不了）。同时**重排的计算成本随 N 线性增长**：本库 9 条无感，生产上 N=20~100 是实打实要计入延迟与费用的项。**结论：本实验证明的是"在召回已经够全的前提下，Rerank 能显著改善排序"，外推到真实规模需重跑并额外监控 Recall@N。**

### 7. 与 Day 44 基线对得上，实验可复现

"无重排 K=3" 得到 **5/7，错 C1/C6**，与 Day 44 的 K=3（5/7，错 C1/C6）**完全一致**；"无重排 K=5" 得到 **7/7**，也与 Day 44 一致。**同一个测试集、同一个判分口径下跨天复现，说明这两天的数字是稳定可比的**（Day 44 已经警告过 temperature=0 不消除方差，这里 C1/C5 的向量 Top1 顺序在重排前后有交换，但都不影响判分）。

### 8. 顺手修正了 Day 45 留下的一个工程债：阈值默认改为"不启用"

Day 45 实验证明固定全局阈值（0.7）在本库净亏，但 `/api/rag` 当时把 0.7 写成了缺省值——也就是说 **API 一上线就在误杀 C1/C6**。今天把缺省改成"不启用"（只有显式传 `threshold` 或设 `RAG_THRESHOLD` 才过滤），同时把 Rerank 设为默认开启。**这是"实验结论要真的落回产品代码，否则实验白做"的正面例子。**

## 概念卡片

- **粗排（Retrieve / 召回）**：向量检索把候选从全库缩到 TopN，追求"别漏"，常牺牲排序精度。
- **精排（Rerank）**：对候选逐条与 query 做精细相关性打分并重排，追求"把对的排前面"，只处理 N 条所以可以更贵更准。
- **双塔（bi-encoder） vs 交叉编码器（cross-encoder）**：前者 query 和文档**各自**编码成向量（可离线预计算、快，但丢了交互细节）；后者把两者**拼在一起**过模型（慢、不能预计算，但准）——这就是 Rerank 的代价与价值来源。
- **倒排/词重合打分器（lexical overlap）**：本日的 Mock，用字符二元组 Dice 系数衡量字面重合；无分词、零成本、可离线，但不懂同义改述。
- **稳定排序（stable sort）**：同分保持原有（向量）顺序；本题里它决定"全 0 分的库外问题"顺序不被重排打乱。

## 面试题

### Q1：向量检索已经是语义检索了，为什么还需要 Rerank？
A：因为**召回和排序是两件事**。向量检索用双塔模型把 query 和文档各自压成一个向量，**压的过程中丢掉了 query 与文档之间的细粒度交互**，所以"召回得到"不等于"排得准"。本实验就是活证据：C1「响应式原理是什么？」的 gold `vue3.md#响应式原理` 向量排名第 5、距离 0.800，而噪声 `react.md#渲染机制` 只 0.554 就排在第 1——**向量 Top1 是错的**。加上 Rerank 后 gold 从第 5 提到第 1，K=3 的正确率从 5/7 变成 7/7。Rerank 用交叉编码器把 query 和文档拼起来过模型，能补回这部分丢失的交互信息。

### Q2：加了 Rerank 之后，TopK 应该调大还是调小？
A：应该**调小**。本实验里"重排 N20→3"和"无重排 K=5"正确率都是 7/7，但前者平均噪声只有 1.57（后者 3.86）、prompt 估算 ≈3144（后者 ≈4041，省 22%）；而"重排 N20→5"正确率一点没涨（还是 7/7），噪声和 token 却都更大——因为精排已经把正确内容挤到前 2 位，第 4、5 位是 `react.md#渲染机制(0.00)` 这种零分陪跑。**所以上了 Rerank，K 取 3 就够，大 K 只是延续"重排前靠加大 K 硬凑"的旧习惯。**

### Q3：给 Rerank 配一个"词重合度"打分器，能替代真实 Rerank 模型吗？
A：不能，它只能占位。本实验的 Mock 用字符二元组 Dice 系数，**只会奖励字面重合**：C1 的第 3 位是 `vue3.md#组件定义(0.02)`（正文碰巧含"定义响应式数据"），C2/C3 的第 3 位是 `vue3.md#生命周期(0.09)`，分数从 0.19 直接掉到 0.03，**没有梯度，本质是"有重合/没重合"的二段判别**。它能压掉明显不相干的内容（因此增益方向是对的），但分不清两个都有字面重合的 chunk 谁更相关，也不懂同义改述。生产必须换 cross-encoder——这也是本实验只能证明"链路可行 + 增益方向正确"，不能用来标定真实 Rerank 收益上限的原因。
