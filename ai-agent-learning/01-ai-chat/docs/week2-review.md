## 二、一条主线：Prompt 的「塑形 → 加固 → 兜底」

六天不是六个孤立技巧，而是一条递进的信任链——**目标是让 LLM 输出从"能看"变成"能被程序安全消费"**。

```text
Day 8  发现：System Prompt 能改变输出的长度/结构/视角（现象层）
  ↓
Day 9  杠杆：示例能教模型"判定边界"，比讲道理有效（Prompt 层）
  ↓
Day 10 契约：JSON Mode + Zod，让输出有可验证的结构（结构层）
  ↓
Day 11 警醒：结构合法 ≠ 内容忠实——模型会脑补（语义层）
  ↓
Day 12 兜底：失败路径（超时/限流/空响应/截断）也要有确定行为（韧性层）
  ↓
Day 13 整合：以上全部，靠"跑→看→改"的迭代闭环沉淀为方法（方法论层）
```

三个反复出现、被多次实验交叉验证的结论：

1. **「给字段名」≠「给标准」**。Day 9 模型把「包装完好」误判为 positive；Day 11 模型给极简需求自创接口；Day 13 priority 标准漂移（资金异常与咨询同评"中"）。缺的都是可操作的判定边界，而不是字段定义。
2. **抽象规则立框架，具体示例定边界**。Day 9 中 3 条示例即把 9/10 拉到 10/10；Day 13 规则文字修不好的闪退降级，2 条对比示例一次纠正。但示例必须少而精、类别平衡、且与测试集隔离（防样例泄漏）。
3. **约束要分层**：prompt 只是"请求配合"，JSON Mode / Zod / RequestOptions 才是"强制"。Day 12 进一步把 `maxRetries: 0`、超时收到应用层统一控制——**能交给 API 保证的，不依赖模型自觉；模型自觉只用来做兜底**。

## 三、计划面试题作答（4 题，证据均来自本周实验）

### Q1：Structured Output 解决什么问题？

解决「LLM 输出无法被程序可靠消费」的问题。自由文本每次格式都可能不同，下游只能靠脆弱的正则猜；Structured Output 让模型输出符合约定 schema 的 JSON，程序拿到的是**确定字段、确定类型、可直接反序列化**的数据。

但本周实验精确界定了它的能力边界：

- 它**只保证结构**：Day 10 中 `finish_reason=length` 导致半截 JSON，说明 JSON Mode 不防截断——必须配合 max_tokens 预估与 Zod 校验；
- 它**不保证语义**：Day 11 模型输出的 JSON 结构完全合法，内容却是脑补的页面和接口。

所以准确说法是：Structured Output 把"不可解析"风险降到接近零，把"内容不可信"风险留给 prompt 约束与人工确认。

### Q2：Prompt 为什么会影响结果？

因为 LLM 是基于概率的生成模型，prompt 是它生成时**唯一的条件输入**——换 prompt 就是换生成所依据的概率分布。本周实验给出了三类可观察的影响机制：

- **Role 改变筛选坐标系**：Day 8 中「面试官」prompt 让模型主动追问，「新手老师」prompt 让它全程知识降维；
- **Instruction 改变输出空间**：Day 8 强格式指令把 completion 从 619 tokens 压到 116；
- **示例改变判定边界**：Day 9/13 中 few-shot 直接纠正了模型对中性评论、闪退优先级的判断。

反过来这也意味着：prompt 里没写的约束，模型没有义务遵守——Day 11 朴素 prompt 下模型默认"尽力完成任务"而非"质疑任务"，才会把闲聊做成软件方案。

### Q3：为什么生产环境不能完全信任 LLM 输出？

因为错误会同时出现在四个层面，且每一层的检测手段不同：

| 层面 | 本周真实案例 | 兜底手段 |
|---|---|---|
| 网络层 | Day 9 静默挂死 4 分钟；Day 12 hang 场景 | 显式超时 + 限次重试 |
| 结构层 | Day 10 半截 JSON（length） | JSON Mode + Zod + 回喂修复 |
| 语义层 | Day 11 脑补页面/接口、误归类 | 反幻觉 prompt、待澄清机制、评测集 |
| 行为层 | Day 13 越权诱导（要求承诺退款） | 动作白名单措辞 + 权限隔离 |

共同的工程姿态：**所有输出先校验、再使用；信息不足让模型提问而不是脑补；系统在失败路径下降级而不是崩溃**。LLM 输出应定位为"草稿/建议"，关键决策（资金、权限、排期）必须有人类或确定性代码的确认环节。

### Q4：JSON Schema 有什么作用？

JSON Schema 是输出的**契约**，在本周承担三个角色：

1. **校验门**：程序在消费数据前验证字段名、类型、必填项、枚举值，不合法直接拦截——把错误挡在下游系统之外（Day 10/13）；
2. **错误信息源**：校验失败后，精确的报错（如 `module: Expected string, received number`）回喂模型，修复轮有的放矢，而不是笼统地说"你错了重写"（Day 10 实测 1 轮修复即成功）；
3. **协作契约**：schema 是前后端、人机之间的接口约定。本周用 Zod（TypeScript 生态）定义 schema，还能反推出静态类型，校验与类型共用同一份定义。

同样要记住它的边界：schema 描述的是"形状"，无法约束"这个字段的值是否忠于用户输入"——后者属于 Day 11 的语义层。

## 四、薄弱点与遗留问题（诚实记录）

1. **P0/P1/P2 的判定仍依赖我给的 gold**：真实工单分诊中"影响面"需要线上数据（多少用户、什么链路）支撑，目前的 10 条测试集是教学规模，不能代表真实分布。
2. **Day 12 的成本数字为估算**：超时/报错响应不返回 usage，R3/R4 的 token 数当时未逐条落盘，costs.md 中标记为估算——后续实验应在脚本内自行累加真实 usage 并输出。
3. **流式（SSE）场景下的错误恢复本周未覆盖**：Day 12 的恢复链路基于非流式响应，Day 15 之后进入 Tool Calling，需要重新考虑流式中如何检测截断与工具调用错误。
4. **上下文缓存仅停留在推断**：Day 13 提到 system 前缀可命中缓存，但未在 DeepSeek 上做带缓存命中字段的验证。
