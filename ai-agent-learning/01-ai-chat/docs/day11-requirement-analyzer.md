# Day 11：需求分析器实验

> 日期：2026-10-03
> 模型：deepseek-chat（temperature=0，全部启用 JSON Mode）
> 任务：一句话需求 → `{ module, pages, components, api, risks }`
> API 调用：16 次，prompt 3792 tokens / completion 2252 tokens

## 实验设计

在 Day 10 三层防线（JSON Mode + Zod + 回喂修复）的基础上，对比两种 system prompt：

- **A 基础 prompt**：只描述输出结构——观察模型对模糊需求的"脑补"行为
- **B 反幻觉 prompt**：增加四条规则——只许基于用户明确提到的信息；信息不足在 risks 写"待澄清：xxx"；
  无关输入 module 留空；risks 可结合领域常识但不许编造细节

## 总览

| 策略 | Schema 通过 | 修复触发 | 关键词命中 | "待澄清"条数 | Prompt Tokens | Completion Tokens |
|---|---|---|---|---|---|---|
| A 基础 prompt（只描述输出结构，无反幻觉约束） | 8/8 | — | 26/27 | 0 | 1328 | 1133 |
| B 反幻觉 prompt（同结构 + 忠于输入/待澄清/无关判定规则） | 8/8 | — | 27/27 | 27 | 2464 | 1119 |

    "待澄清：是否需要限制换绑频率？",
    "业务风险：手机号是重要身份凭证，换绑流程需防范恶意操作，确保账号安全。"

## 分析与学习笔记

### 1. 脑补的铁证：模型会把任何输入都往"需求模板"里套

用例 6「今天晚上吃什么好呢」是全场最鲜明的对比：

| 策略 | module | pages / api | 结果 |
|---|---|---|---|
| A 基础 prompt | "晚餐选择" | 晚餐推荐页 / 获取随机晚餐推荐接口 | 把闲聊**当成真需求做了完整方案** |
| B 反幻觉 prompt | ""（空） | 全空，risks 说明"与软件开发无关" | ✅ 正确拒绝 |

用例 7 的注入句同理：A 没有讲笑话（JSON 格式约束守住了），却凭空编造出一个"用户登录"模块——"随便写的JSON"被它用最常见的登录需求填充了。**这说明 LLM 倾向于"尽力完成任务"而不是"质疑任务是否成立"**：没有明确的拒判规则时，它默认任何输入都是合法需求。Schema 校验对此完全无能为力——输出的结构 100% 合法，错的是内容。

### 2. "合理推断"还是"擅自加需求"：完整需求下的范围蔓延

即使用例 1（计划示例句）这种信息完整的输入，A 的输出也明显比 B"丰满"，而多出来的条目用户一个都没提：

- **用例 1**：A 加了「交易明细页」「打印凭条接口」「银行卡读取组件」
- **用例 3**：A 加了「检查商品是否已收藏接口」（B 只给收藏/取消收藏两个接口）
- **用例 4**：A 加了「支付按钮」「提交挂号订单」「取消挂号」——用户只说"选科室医生、看号源"，没说要在线挂号成交

这些推断里，有些是资深分析师的合理发挥（账户查询配密码验证），有些则是典型的范围蔓延（支付、打印凭条）。**危险之处在于：输出格式越工整，下游（开发、排期）越容易把它当成已确认的需求照单全收。** B 的做法是把不确定项全部移到 risks 并以"待澄清"开头，pages/api 只保留用户明确说过的内容——同样的信息，呈现出的"确定 vs 待定"边界完全不同。

### 3. 一个典型行为：A 一边提醒"未明确"，一边按"已明确"来做

用例 2「做个登录」中，A 的 risks 里老实写了"是否需要图形验证码未确认"，但 api 数组里已经把「获取图形验证码接口」列上了。**提醒归提醒，方案照做**——如果直接拿 A 的 api 数组排期，那些"未确认"就被默认确认了。B 则只保留 1 个登录验证接口，把验证码、登录方式、跳转目标全部列为待澄清。这是两种 prompt 最本质的差别：A 的 risks 与其他字段是"平行的备注"，B 的待澄清项是"阻断下游使用的前置条件"。

### 4. 反幻觉 prompt 的代价：过度提问 + 1.9 倍 prompt token

B 并非没有缺点：

- **过度提问**：8 条用例产出 27 条待澄清，平均每条 3.4 个问题。用例 1 中"是否需要身份验证（密码、指纹）"对银行自助终端几乎是必然项，仍被列为待澄清——规则让模型变得机械、"不敢负责"。
- **成本**：B 的 system prompt 更长，prompt tokens 2464 vs A 的 1328（约 1.9 倍）；completion 两者相近（1119 vs 1133），B 用更短的方案条目换出了提问空间，总 token 反而略低。
- 生产中的折中：可以在规则里区分"必须澄清"（影响范围/报价的项）与"可按行业默认假设"（并在 risks 标注假设内容），让模型既不沉默脑补，也不把所有决策抛回给用户。

### 5. 工程定位：分析器的产出是"结构化草稿"，不是"需求结论"

两种策略在领域风险识别上都在线：银行场景抓到密码安全/隐私泄露，医疗场景抓到患者隐私/号源并发，OA 场景抓到万人并发/数据不丢。所以这个分析器的正确用法是——**帮助人快速产出可讨论的初稿 + 风险清单初稿，所有"待澄清"必须回到真实需求方闭环，确认后的条目才能进入排期。** 这也正是 Day 72 Product Agent 会复用本结构的原因：Agent 的结构化输出后面必须接一个人类（或 Manager Agent）的确认环节。

### 6. 成本

16 次 API 调用（8 用例 × 2 策略，0 次修复），prompt 3792 / completion 2252 tokens ≈ ¥0.005。本次无修复支出——温度 0 + JSON Mode 下结构化输出已相当稳定，风险全部集中在语义层而非结构层。

## 概念卡片

- **需求分析器**：把自然语言的一句话需求转成 `{module, pages, components, api, risks}` 结构化开发方案的 LLM 应用，本质是 Structured Output 的垂直场景落地。
- **脑补（Silent Hallucination）**：模型在信息不足时不提问、不拒答，直接用训练数据中的常见模式补全需求。结构合法、语义失真，Schema 校验无法发现。
- **待澄清机制**：把信息缺口显式写进 risks（"待澄清：xxx"），让不确定项成为阻断下游使用的前置条件，而不是平行的备注。
- **范围蔓延（Scope Creep）**：模型把"合理的领域推断"直接写成确定的页面/接口，可能被下游当成已确认需求，导致报价和开发范围扩大。

## 面试题

Q：需求分析器如何避免模型脑补用户没提过的功能？
> A：三层手段：① prompt 显式规定"只能基于用户明确提到的信息"，信息不足时在 risks 写"待澄清"问题、无关输入直接拒判（module 留空）；② 输出经 Zod 等 schema 校验保证结构；③ 流程上把分析器产出定为"草稿"，待澄清项必须经需求方确认后才能进入排期。实验证明没有第①层时，模型会把"今天吃什么"都分析成带页面和接口的软件需求。

Q：结构化输出的 schema 校验能发现需求分析器的所有错误吗？
> A：不能。Schema 只保证字段名、类型、枚举等**结构**合法；模型脑补的页面、误判的模块、错放的领域风险，结构上全都合法，属于**语义**错误，只能靠 prompt 约束（反幻觉/待澄清）、评测集和人工确认来兜底。这与 Day 10 "语法合法 ≠ 语义正确"的结论一脉相承。

Q：给 LLM 加反幻觉约束有没有成本？
> A：有。① prompt 变长使输入 token 上升（本次约 1.9 倍）；② 模型可能过度提问，把行业内近乎默认的事项也列为待澄清，显得不敢担责；③ 提问过多会增加需求方的沟通成本。工程上要区分"必须澄清"和"可按默认假设并标注"的事项，而不是一刀切。
