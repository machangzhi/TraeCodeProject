# Day 13：Prompt 优化实验（V1 → V2 → V3）

> 日期：2026-10-04
> 模型：deepseek-chat（temperature=0）
> 场景：技术支持工单分诊，输出 {category, priority, summary, suggested_action}
> 方法论：测试集 10 条固定不变，唯一变量是 prompt；V2/V3 基于上一版"真实输出问题"迭代。

## 指标总览

| 版本 | JSON可解析 | 夹散文条数 | 类别正确 | 优先级正确 | 摘要超30字 | 越权承诺 | Prompt Tokens | Completion Tokens |
|---|---|---|---|---|---|---|---|---|
| V1 朴素版 | 10/10 | 1 | 0/10 | 0/10 | 4 | 0 | 695 | 1017 |

# V1 朴素版

```text
你是一个技术支持团队的工单分诊助手。请分析用户提交的问题，输出一个JSON对象，包含以下字段：
- category：问题类别
- priority：优先级
- summary：问题摘要
- suggested_action：建议的处理方式
```

#### 用例 1（全站核心链路中断）
输入：线上支付全部失败，用户都在投诉，已经持续10分钟了！

判定：❌类别 ❌优先级

原始输出：

```text
{
  "category": "支付系统故障",
  "priority": "紧急",
  "summary": "线上支付全部失败，持续10分钟，用户投诉激增",
  "suggested_action": "立即通知支付系统运维团队和值班工程师，启动最高级别故障响应，排查支付网关、数据库、第三方支付接口等关键环节，同时向用户发布故障公告并安抚投诉用户"
}
```

# V2 规则版

```text
你是技术支持团队的工单分诊助手。分析用户提交的内容，只输出一个JSON对象，不要输出解释文字或markdown代码块：
{
  "category": "问题类别",
  "priority": "优先级",
  "summary": "问题摘要",
  "suggested_action": "建议的下一步处理"
}

【category 只能取以下枚举之一】
- bug：产品功能报错、崩溃、数据或显示异常
- how_to：使用咨询、询问操作方法（功能本身正常）
- billing：扣费、退款、账单、发票等资金相关
- account：登录、注册、密码、验证码、账号绑定等账号问题
- feature_request：新功能或产品改进建议
- other：与上述无关、或无实质问题的内容（如表扬、寒暄）

【priority 只能取 P0/P1/P2/P3 之一，判定标准如下】
- P0：全站或核心链路（支付、登录）不可用，大面积用户受损，需立即响应
- P1：核心功能异常、资金问题、导致用户无法完成关键操作
- P2：非核心功能缺陷、显示或一致性问题，存在临时规避办法
- P3：使用咨询、功能建议
当 category=other，或内容信息不足无法判断时，priority 输出 null，禁止硬给优先级。

【其他规则】
- summary 不超过30字，只概括"什么出了问题"，不要写原因分析或诊断
- suggested_action 只能写"建议核实/转交/按流程处理"，禁止替公司承诺退款或赔偿，不得出现"已退款""保证赔偿"等措辞
- 信息严重不足时，category 和 priority 都输出 null，summary 以"信息不足："开头说明需要用户补充什么
```

## 迭代记录与方法论

### 五要素对照（输入 / 输出 / 问题 / 修改 / 效果）

三个版本共用完全相同的 10 条输入（见上文各用例），输出均完整保留在上文。问题、修改与效果对照如下：

| | V1 朴素版 | → V2 规则版 | → V3 规则+格式+示例 |
|---|---|---|---|
| **实测问题** | category 自由创词（0/10）；priority 用自然语言且标准漂移（0/10，资金异常与咨询同评"中"）；4 条摘要超 30 字、夹带诊断；1 条夹代码块；表扬/信息不足仍硬给优先级 | 残留：闪退因"偶发"被误降到 P2（9/10）；纯 JSON 只靠 prompt 请求、无硬保证 | —（已收敛） |
| **修改点** | 只给了角色 + 4 个字段名 | ① category 锁 6 个枚举并各配定义 ② priority 锁 P0–P3 并给判定标准 ③ 摘要限 30 字、禁止诊断 ④ 禁止代码块 ⑤ other + null 处理表扬/信息不足 ⑥ 禁止越权承诺 | ① 开启 JSON Mode（格式由 API 强制）② 加 2 条测试集外的边界示例：闪退≥P1 vs 显示延迟=P2 |
| **最终效果** | 可解析 10/10，但类别/类别化判定不可用 | 类别 10/10、优先级 9/10、摘要 0 超长、越权 0 | 类别 **10/10**、优先级 **10/10**、摘要 0、越权 0、夹散文 0 |

### 沉淀：Prompt 优化的 6 条方法论

1. **问题要"跑出来"，不要"想出来"**。V2/V3 的每一条修改都对应 V1/V2 输出里的具体证据，而不是"我觉得模型可能会错"。先跑、再看、后改，是 prompt 优化与拍脑袋改 prompt 的根本区别。

2. **测试集固定，唯一变量是 prompt**。10 条输入贯穿三版不变，指标变化才能归因到 prompt；如果每版顺手换用例，就无法判断是 prompt 变好了还是用例变简单了。

3. **"给字段名" ≠ "给标准"**。V1 写了 `priority` 字段却没给判定标准，模型只能各凭理解——结果资金异常和使用咨询同评"中"。枚举值 + 每档的可操作定义，才是在给模型"判定边界"。

4. **边界用示例锚定，比堆砌规则文字有效**。V2 的规则里其实已写明"崩溃不属于显示问题"，模型仍把闪退降到 P2；V3 只加了两个对比示例（闪退→P1 / 已读状态延迟→P2），错误立即纠正。抽象规则负责立框架，具体示例负责教边界——与 Day 9 Few-Shot 的结论一致，且示例必须取自测试集之外防止"背答案"。

5. **约束分层：prompt 能请求的，用 API 强制**。格式在 V2 靠"请只输出 JSON"（请求），V3 靠 JSON Mode（强制）。能用结构化输出/API 参数保证的，就不要只写在 prompt 里——prompt 是"请求模型配合"，API 约束才是"不给错误选项"。

6. **客观评价，不造稻草人**。V1 并非一无是处：面对越权诱导，它主动选择了"按流程处理、上报法务"而没有承诺退款（越权 0）。V2 要做的是把这种**偶发的正确**沉淀成**稳定的规则**，而不是假装 V1 全错来衬托优化成果。

### 一个反直觉的成本现象

三版 prompt 越来越长（Prompt Tokens 695 → 3945 → 6015，总 token V1=1712 / V2=4499 / V3=6384），但 Completion Tokens 反而 **1017 → 554 → 369**。核心规律是：**清晰的规则和枚举让模型输出更短、更确定**，不用写长篇编号列表（对比 V1 用例2 的 4 条编号建议与 V3 一句话"建议转交客户端研发排查"）。规则的投入集中在 system 侧、每版固定不变，且 system 前缀可命中上下文缓存，规模化调用后边际成本很低。

## 概念卡片

- **Prompt 迭代闭环**：朴素 V1 → 固定输入验证 → 归纳真实问题 → 针对性修改 V2 → 再验证 → V3 收敛。
- **判定标准 vs 字段名**：字段名只规定"输出什么"，枚举 + 每档定义才规定"怎么判"，缺后者必然标准漂移。
- **边界示例**：取自测试集之外、专门锚定两个相邻档位（如 P1/P2）分界的 few-shot，对规则的补充作用强于增加规则文字。
- **约束分层**：prompt 请求 < JSON Mode/Schema 强制；能由 API 保证的约束不依赖模型自觉。

## 面试题

Q：你是怎么优化一个 LLM Prompt 的？讲讲实际过程。
> A：不是凭感觉改，而是迭代闭环：① 先写朴素 V1；② 建一批固定测试输入跑，如实保留输出；③ 从真实输出归纳问题（如类别自由创词、优先级标准漂移、摘要超长）；④ 一次针对这些问题修改成 V2（加枚举、判定标准、长度约束、异常输入处理），测试集不变再验证；⑤ 对残留边界问题（闪退被误降级），用测试集外的边界示例 + JSON Mode 出 V3，直到指标收敛。本次三版从类别 0/10、优先级 0/10 收敛到双 10/10。

Q：为什么 Prompt 写清楚字段还不够？
> A：字段名只约束"输出结构"，不约束"判定标准"。只给 priority 字段而不定义每档标准，模型会自由发挥：本次 V1 把重复扣费（资金异常）和咨询操作都评为"中"，区分度被压缩。必须给封闭枚举和每档的可操作定义，而抽象标准在边界上仍可能失效（闪退被误降到 P2），这时要用具体示例锚定边界。

Q：加规则和示例会不会让成本失控？
> A：主要增加的是 system prompt（输入侧），本次 Prompt Tokens 随版本增长，但输出因规则更清晰而从 1017 降到 369；system 前缀还能命中上下文缓存，规模化后边际成本低。真正要控制的是示例数量——只锚定真实出错的边界，少而精，而不是把大量示例堆进 prompt。
