## 学习笔记

### 1. 工具集扩大后，问题从「会不会调」变成「选得准不准」

只有一两个工具时，调用几乎是二选一；今天 4 个工具同时在线，判分必须分两层看：

- **工具选择层**：该调的调了没有（expectedTools）？有没有调名单外的（allowedTools 白名单）；
- **答案层**：最终答复与 gold 是否一致。

两层解耦很有必要——S4 就是典型：答案完全正确，但工具选择有瑕疵。如果只看答案正确率 8/8，会以为一切完美；只看工具选择，又会漏掉"答案其实可用"。生产中这两层对应不同的改进手段：选择差→优化工具描述/规则，答案差→检查工具返回与推理。

今天的选择矩阵显示模型对「直选」（S1-4）、「消歧」（S5 把"带伞"正确翻译成 weather）、「克制」（S7 水沸点零调用）、「并行/链式」（S6/S8）全部判对，唯一失分是 S4 的**过度调用**。

### 2. S4：过度热心的额外工具调用（两轮稳定复现）

S4 用户只问"股价多少"，模型两轮实验都在 search 之后**主动加调 calculator 算涨幅**，还给出了完整的投资风险提示。这不是随机噪声——两轮独立运行行为一致，是稳定的行为倾向：

- 动机可以理解：搜索结果里同时含现价和前收盘价，模型"看到就算"，且预判了用户下一个问题（S6 恰好就是涨幅）；
- 代价真实存在：多一次 API 轮次（2 轮→3 轮，延迟增加）、多一次 calculator 调用与 token；
- 怎么评价取决于场景：面向终端用户，主动信息可能是好体验；面向成本敏感的批处理/严格按需求执行的系统，这就是越界。

工程对策：① system 明确"只回答被问到的，不主动计算衍生指标"；② 如仍不放心，可在执行层用工具白名单/预算限制（allowedTools 思路的运行时化）。注意这与 S7 的"克制"形成有趣对照：模型对"该不该用搜索"判断准确（常识不搜），但对"搜到的信息要不要进一步加工"容易过度——**调用克制的难点在边界细节，不在大类**。

### 3. S6 链式、S8 并行：依赖分析继续稳定

- S6：模型先 search 拿到 252.14/240.50，再用 calculator 算 `(252.14-240.50)/240.50*100=4.84%`，涨幅数字来自工具而非心算；
- S8：天气与股价互不依赖，同轮并行发起，两个 gold（27°C / 227.73）都命中。

Day 19 L3 的链式规划今天再次复现，说明这不是偶发。值得注意 S4 和 S6 调用了**完全相同的两个工具、参数都一样**，区别只在用户是否问了涨幅——模型的行为差异完全由用户意图驱动，这是"工具使用服从于需求理解"的直接证据。

### 4. 第三次判分器事故：gold 手误 → gold 必须来自实现

S1 首跑误判 ❌，追查发现 calculator 返回 7,006,652 完全正确，是我手敲 gold 时写成了 7,007,542（Day 16 另一题的数字串记忆）。这已经是连续第三次判分器问题：

| 日期 | 事故类型 | 后果 |
|---|---|---|
| Day 16 | 判分器误放（正文数字/伪标签采信） | 虚高 |
| Day 17 | 判分器误杀（只认连字符格式） | 虚低 |
| Day 20 | gold 手误（手敲错误数字） | 虚低 |

修复原则沉淀为硬规则：**gold 一律由内置确定性实现实时算出（calculate(...)），禁止人工硬编码数字**。判分器本身也是被测对象——先用人脑可验证的简单 case 校准判分器，再相信它给出的成绩。

### 5. 工具集规模与成本的关系

今天定稿轮 prompt 11617 tokens，是 Day 19（4785）的 2.4 倍——涨幅全部来自第 4 个工具的 JSON Schema 定义，且每个场景每次 API 调用都要重发全量工具定义，多轮场景被放大（S4/S6 三轮）。结论：**工具越多，每轮固定税越重**。工程对策（后续周会用到）：① 按场景裁剪工具集（不同路由暴露不同子集）；② 工具描述保持精炼；③ 高频场景考虑 prompt 缓存。

## 概念卡片

- **工具选择两层判分**：选择层（expectedTools/allowedTools）与答案层（gold）解耦，分别暴露"选错"与"答错"。
- **过度调用（over-calling）**：用户未要求的衍生计算/额外工具往返，体现模型的主动倾向；成本与收益依场景而定。
- **工具固定税**：全量工具定义随每次请求发送，工具集扩大推高每轮 prompt 成本。
- **gold 同源原则**：标准答案由被测的确定性实现产出，禁止手敲。

## 面试题

Q：工具数量增加后，评测方法要做什么调整？
> A：判分拆成两层：工具选择层（该调的调了没、有没有调白名单外的）与答案层（gold 对不对）。今天 S4 答案对但多调了 calculator，单层判分必然漏掉。我们用选择矩阵（场景×工具）+ 两层指标，定稿选择 7/8、答案 8/8。

Q：模型会不会多调工具？怎么发现和处理？
> A：会，而且可能稳定复现——S4 用户只问股价，模型搜索后主动加算涨幅，两轮行为一致，多一整轮延迟和 token。发现手段是 allowedTools 白名单：出现名单外调用即标记。处理依场景：面向成本敏感系统可在 system 加"只回答被问到的"，并在执行层做工具预算；主动信息在 C 端则可能是好体验。

Q：工具多了成本会怎样变化？
> A：每轮请求都要携带全量工具的 JSON Schema 定义，形成随工具数增长的"固定税"。今天加第 4 个工具后 prompt 用量是 Day 19 的 2.4 倍，多轮场景更明显。对策：按路由暴露工具子集、精炼工具描述、高频场景用 prompt 缓存。

Q：你们怎么保证评测用的标准答案正确？
> A：踩过坑——gold 手敲曾写错导致 S1 误判。规则是 gold 必须由内置确定性实现实时计算（calculate 同源），禁止硬编码。判分器自身也要先用可心算的简单 case 校准，Day 16/17/20 连续三次判分器事故（误放、误杀、gold 错）促使我们把"判分器也是被测对象"写进流程。
