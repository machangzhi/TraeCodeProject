## 学习笔记

### 1. 工具升级：从「能跑协议」到「返回可直接使用的结构化事实」

Day 15 的 time 工具只返回一段格式化字符串。今天的正式版返回 8 个字段：`timezone / iso / local / hourMinute / date / weekday / offsetMinutes / abbreviation`。意义在于——用户问"周几、几号、时差"时，这些都是**工具算好的确定事实**，模型只需读取转述，不必自己心算跨时区偏移（心算时区几乎必错：要处理夏令时、日期变更线）。S5 实测：模型准确给出洛杉矶"星期日 00:58、UTC-7、PDT"，与北京"15 小时时差"，并额外说明夏令时结束后时差变为 16 小时——它连"夏令时会改变偏移"都没有靠猜，PDT/offsetMinutes 都是工具字段。

### 2. 时区校验：用运行时能力当验证器，而不是维护时区名单

校验没有用 IANA 时区清单（几百条、还会更新），而是直接试构造 `new Intl.DateTimeFormat("en-US", { timeZone })`：合法时区正常返回，非法时区抛 RangeError。S7 实测 `Atlantis/Nowhere` 被确定性拦截，工具返回 `{"error":"非法时区：..."}`，模型转述错误并明确"我不能凭猜测给你一个时间"，还给出了补救路径（提供城市名或正确 IANA 名）。这与 Day 16「让程序做它擅长的事」是同一思想：**把知识密集且易过期的校验交给运行时，错误穿透返回**。

### 3. 城市名翻译在模型、时区合法性在工具：一道清晰的契约边界

- S3"东京现在几点"：模型把城市名翻译成 `Asia/Tokyo` 再调用——翻译是语言任务，模型承担；
- S6"火星上现在几点"：模型**一次工具都没调用**，直接说明"火星不在 IANA 体系内"，还补充了火星协调时 MTC、火星日 sol≈24h39m 的背景。

S6 值得对照 Day 16：那时模型面对办不到的事会"演一个工具"，这次它在调用前就判断出没有合法参数，选择不调用、直接解释。说明模型的"调用门"可以被 prompt 调教得更聪明；同时也要意识到**这一层判断仍在模型手里，不可全靠它**——如果用户诱导（把火星伪装成"时区 Mars/Olympus"），工具层的校验才是最后防线，今天 S7 证明了防线有效。

### 4. 并行调用已是成熟模式：S4/S5 一轮两个申请

S4（纽约+伦敦）和 S5（洛杉矶+北京）模型都在同一轮并行发出两个 tool_calls，程序逐一执行、逐一回传，模型拿到两份同一瞬间（iso 相同）的事实后统一组织答复。Day 15 首次踩过的"并行调用必须逐一配对"坑，今天的编排循环直接正确处理。另一个细节：S5 的时差依赖**同一瞬间**的两个 offset——工具返回的 iso 字段让"同一时刻"可被验证，避免了两次调用间隔造成的误差争议。

### 5. 判分器误杀的完整修复：基础修正 → 正则加固 → 单测校准 → 重跑确认

问题：S5 首轮模型答复完全正确（"2026年10月4日"），判分器却只接受连字符格式（`text.includes("10-04")`），误判 ❌——false negative。

修复分两步：
1. 先补了"10月4日"字符串匹配，重跑 8/8；
2. 复查时发现这版写死了无零头格式，对"10月04日""2026年10月4日"仍会误杀，于是改用由 gold 构造的正则：

```text
(2026[-年/])?0?10[-月/]0?4日?
```

兼容可选年份、`-` 与 年/月/日 两种分隔、日月前导零。修复后先用 7 条已知对错样本单测校准（5 种正确写法应命中、"10月5日"与"00:04"应拒绝，全部 PASS，临时测试文件用完即删），再重跑全量 8/8 定稿。

对照 Day 16 判分器的"误放"（false positive）：**评测系统的两类错误都会污染结论，字符串硬匹配天然脆弱——多格式字段优先用构造式正则，且每次新增场景都要用已知对错样本先校准判分器，再相信评测成绩**。

### 6. 不需要调用时的克制：S1 默认参数 与 S8 零调用

- S1 用户不给时区，模型调用时省略参数，工具按默认 `Asia/Shanghai` 处理并在结果中写明实际时区——默认值的实际生效情况对模型可见，防止"用户以为查的是老家时间"的歧义；
- S8 问 UTC/GMT 区别，模型零工具调用，一句话讲清"UTC 基于原子钟+闰秒、GMT 基于格林尼治太阳时，日常值几乎相同"。时间常识不需要实时工具，调用门再次工作。

## 概念卡片

- **IANA 时区数据库**：全球时区的标准命名与规则库（Asia/Shanghai 等），包含夏令时规则；Intl API 内置其数据。
- **时区校验器（Intl 探针）**：用 `new Intl.DateTimeFormat(..., {timeZone})` 是否抛 RangeError 判断时区合法性，无需自行维护名单。
- **UTC 偏移（offsetMinutes）**：某地相对 UTC 的分钟差（北京 +480、洛杉矶夏令时 −420）；两地偏移之差即时差，夏令时会使其随季节变化（PDT/PST）。
- **调用门**：模型在调用工具前的决策层——判断问题是否需要工具、参数能否合法构造；可被 prompt 调教，但不是安全边界。
- **默认参数回显**：工具使用默认值时应在返回中写明实际生效值，让默认行为对调用方可观测。

## 面试题

Q：getCurrentTime 怎么校验用户/模型给的时区？为什么不自己维护时区列表？
> A：用 Intl 探针：试构造 `new Intl.DateTimeFormat("en-US", { timeZone })`，非法 IANA 名会抛 RangeError，捕获后返回结构化 `{error}`。不自己维护名单是因为 IANA 数据库有几百个时区且夏令时规则会更新，而运行时 Intl 内置的就是权威数据。今天 S7 实测 Atlantis/Nowhere 被拦截，错误穿透两阶段后模型如实转述，没有编造时间。

Q：用户问"东京几点"和"火星几点"，链路分别怎么走？
> A：东京：模型把城市名翻译成 Asia/Tokyo（语言任务），工具校验合法后返回结构化时间。火星：模型在调用门前就判断火星没有 IANA 时区，一次工具都不调用，直接解释并补充 MTC/火星日背景。但安全上不依赖模型这一层判断——即使模型把火星伪装成时区名发起调用，工具的 Intl 校验会确定性拒绝（S7 已验证）。

Q：问"洛杉矶周几、跟北京差几小时"为什么必须用工具？模型不能自己算吗？
> A：答案同时依赖星期、日期、UTC 偏移和夏令时状态，全是易错题。今天 S5 工具返回同一瞬间洛杉矶 offsetMinutes=-420（PDT）、北京 +480，模型据此准确算出星期日、15 小时时差，并主动说明夏令时结束后变 16 小时——偏移和夏令时缩写都来自工具字段，没有一个是心算。

Q：讲一下这次判分器误杀的修复过程，为什么修了两次？
> A：根因是判分用 `includes("10-04")` 硬匹配，模型写中文"10月4日"被误判 ❌。第一次只补了中文固定写法，复查发现它仍不兼容"10月04日""2026年10月4日"；第二次改为由 gold 构造的正则（兼容年份可选、分隔符、前导零），并用 7 条已知对错样本单测校准通过后，重跑全量 8/8。教训：硬匹配脆弱，多格式字段用构造式正则；判分器改动后必须先用样本校准，这与 Day 16 的"误放"问题互为印证。
