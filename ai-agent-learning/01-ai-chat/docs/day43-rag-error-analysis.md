# Day 43：RAG 问题分析 ——「知识库有答案却答错」的逐层定位

> 日期：2026-10-14
> 主题：构造错误案例，把回答错误归因到 Chunk / Embedding / Retrieval / Prompt 中的**第一个真正失败的层**
> 实验脚本：[day43-rag-error-analysis.ts](file:///d:/TraeCodeProject/ai-agent-learning/01-ai-chat/server/src/experiments/day43-rag-error-analysis.ts)

## 实验设计

唯一变量是**问题本身**，知识库（3 个 Markdown / 9 个 chunk）与 RAG 链路代码全程不动。对每个问题做四层取证：

| 层 | 问题 | 判据 |
|---|---|---|
| L1 Chunk | 答案文本真的进了某个 chunk 吗？ | 期望短语是否落在正确 chunk 的文档里 |
| L2 Embedding | 向量模型把正确 chunk 排第几？ | 正确 chunk 在全量距离排序中的最好名次 |
| L3 Retrieval | 实际 `topK=3` 召回正确 chunk 了吗？ | 正确 chunk 是否在 Top3 内 |
| L4 Prompt | 真实 `ragQuery` 的回答对不对？ | 回答是否命中期望正则 |

若 L4 失败，再做一次 **oracle 对照**：只把正确 chunk 喂给 LLM，看它能不能答对。能答对 ⇒ 锅在上游检索；答错 ⇒ 锅才在 Prompt/LLM。这一步是整个方法的核心：**把"检索错"和"生成错"物理隔离**。

## 分析与学习笔记

### 1. 这次知识库的问题不在 Chunk，也不在 Prompt，全在 Retrieval（诱因 Embedding）

Day 37 把固定长度切分换成按标题结构化切分后，**L1 全 7 例通过**——答案文本都完整落在单个 chunk 内（C3/C5 这类需要两段答案的，两个 gold chunk 也都各自完整）。Part A 的检测器用一个真实的"答案跨 H2"反例 + 一个同段落正例证明了它既能抓到切裂、又不会无条件报警，所以 L1 的全绿不是检测器失灵。

真正的失败集中在 L3：C1、C6 的正确 chunk 在全量排序里**都排到第 5**（共 9 个 chunk），`topK=3` 自然召不回。L2 的排名就是 L3 失败的机制解释——不是 K 设小了，而是向量模型把无关 chunk 排到了前面。

### 2. 不是 Prompt 的锅：oracle 对照 2/2 答对

C1、C6 在只把正确 chunk 喂进 prompt 后，模型都**一次答对**（C1 完整讲出 vue2 的 `Object.defineProperty` 与 vue3 的 `Proxy` 对比，C6 完整列出两套生命周期钩子）。这说明现有 system prompt（拒答约束 + `[n]` 引用）本身没问题，问题 100% 在上游检索。**如果没有 oracle 这一步，很容易误判成"模型不行 / prompt 要重写"，从而在错误的一层上花时间。**

### 3. 反直觉发现：prompt 的"没有资料就说无法回答"会把检索失败"伪装"成合规拒答

C1 的检索 Top3 是 react 渲染机制 / react 状态管理 / vue2 生命周期——全是无关内容。模型严格遵循了 system prompt，回了「根据现有知识库无法回答该问题」。从用户视角看，这不是"答错"，而是"不知道"——**比答错更隐蔽**：因为拒答看起来是一个正确、保守的行为，很难被当成 bug，但知识库里明明有完整答案。这提示：`拒答率` 本身要作为 RAG 的一个监控指标，而不是只统计"答错率"。

### 4. 触发条件清晰：查询缺少能锚定到具体文档的"实体词"

对比 C1 与 C2——同一个主题，C1 问「响应式原理是什么？」gold 排第 5；C2 只在问题前加了「Vue3 的」两个词，gold 立刻排第 1（Top1 距离 0.391，明显比 C1 的 0.554 更锐利）。C3/C4/C5 也都因为含具体框架名/术语而排序正确。反例是 C6：它虽然含 "Vue"，但 "Vue" 同时匹配 vue2/vue3 两份文档的**文档级**语境（两份文档名都叫「VueX 组件开发规范」），而「生命周期」chunk 本身很短（就是一句钩子名列表），语义被稀释，于是 gold 仍排第 5。**结论：泛化的中文短语 + 英文 embedding 模型 = 排序崩塌；模型需要"实体锚点"（框架名、专有名词、API 名）才能把向量拉到位。**

### 5. 弱匹配的距离信号是后面几天的抓手

C1 的 Top3 距离全部 >0.55（0.554 / 0.652 / 0.745），C2 的 Top1 只有 0.391。也就是说，C1 检索到的其实都是"弱相关"内容，只是 `topK=3` 会**无条件凑满 3 条**，把误导性来源也返回给用户看。这直接指向：

- **Day 45 Similarity Threshold**：>0.55 的弱匹配直接拦掉，至少不再展示误导来源；
- **Day 46 Rerank**：用交叉编码器把 gold 从第 5 拉回前列；
- **Day 47 Query Rewrite**：把「响应式原理是什么」这类缺锚点的问题改写/补全为带实体词的可检索查询。

### 6. 对照用例证明管线本身没坏

C7（库外天气问题）正确拒答，且 C2/C3/C4/C5 全链路通过。说明失败不是"链路整体坏了"，而是**特定类型的查询**（宽泛、无实体锚点）触发了 embedding 的排序盲区——这是一个可复现、有明确边界的问题，不是偶发噪声。

## 概念卡片

- **四层定位法（Fault Layering）**：把 RAG 错误按数据流分层取证（Chunk → Embedding → Retrieval → Prompt），根因取"第一个真正失败的层"，而不是最先看到症状的层。
- **Oracle 对照（Oracle Test）**：绕过检索、只把正确答案喂给 LLM。答对 ⇒ 检索的责任；答错 ⇒ 生成的责任。用于把两类错误物理隔离。
- **排序偏差（Ranking Bias）**：正确 chunk 存在于库中且距离可控，但被无关 chunk 排在后面（本例排第 5），本质是 embedding 模型对某类查询的语义区分度不足。
- **实体锚点（Entity Anchoring）**：查询里能唯一指向目标文档的专有名词（框架名 / API 名）。缺锚点时向量漂移，加锚点后排序立刻变锐利（C1→C2 对照）。
- **拒答的双刃剑**：RAG 的"没有资料就拒答"能防幻觉，但也会把检索失败伪装成合规拒答，让召回缺陷更难被发现。

## 面试题

### Q1：RAG 答错了，你怎么快速判断是检索的问题还是生成的问题？
A：做一次 oracle 对照——把"当前系统实际召回的 context"和"人工塞进去的正确答案 context"分别喂给同一个 LLM。若换对 context 后答对，说明锅在检索（本文 C1/C6 都属于这种：gold 排第 5，`topK=3` 召不回，但只喂 gold 后模型 2/2 答对）；若换了 context 仍答错，才轮到 Prompt/模型。先做这个隔离，能避免在错误的一层上重写 prompt。

### Q2：知识库里明明有答案，为什么用户还是得到"无法回答"？
A：因为"库里存在答案"和"检索能召回答案"是两件事。本文 C1 的答案完整存在于 vue2/vue3 的「响应式原理」chunk（L1 通过），但向量模型把它排到全库第 5，`topK=3` 没召回，于是模型看到的全是 react 渲染机制这类无关内容，只能按约束拒答。更隐蔽的是：这个错误从表面看像一次"正确、保守的拒答"，所以要把**拒答率**当成召回质量的监控指标，而不是只看答错率。

### Q3：C1 和 C2 是同一个主题的问题，为什么一个失败一个成功？
A：差别只在实体锚点。C1「响应式原理是什么？」没有任何词把它锚定到某份文档，查询向量在库里漂移，最近的反而是 react 渲染机制（距离 0.554，弱匹配）；C2 加上了「Vue3 的」，gold 立刻排第 1（距离 0.391，明显更锐利）。C6 也印证了同一规律：它含泛化的 "Vue"，但 "Vue" 指向整份文档而非「生命周期」这一节，锚定不足，gold 仍排第 5。结论是这类失败可以用 Query Rewrite（补锚点）或 Rerank（重排）修，而不是改 prompt。
